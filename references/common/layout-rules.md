# Layout Rules — Board Layout Guidelines (v2)

> 系统级通用布局规则（适用于所有板型/元件）。生成 `diagram.json` 时参考。
> v2：布局-走线协同框架（模型无视觉 → 数字规则补偿 + 一体设计）。
> 验证来源：18+ 真实项目 + 用户手动布线模板。

## 核心认知：布局与走线必须协同

```
人类（有视觉）：一开始有"画面" → 元件分布 + 走线同时成型
模型（无视觉）：只能从坐标判断 → 缺空间直觉

→ 布局决定走线可行性，走线反馈布局
→ 一体设计：布局时预判走线，走线时受布局约束
→ 规则 = 把视觉直觉翻译成数字条件（间距阈值/通道/平行）
```

## 协同框架（3 层）

```
① 布局规划（含走线预判）
   元件放哪 → 同时预判每条线走向
   检查：线被遮挡？平行线有空间？通道够？
   位置不对 → 提前调整

② 走线规划（受布局约束）
   线路径 → 检查空间：遮挡/交叉/重叠/平行间距
   不够 → 调整节点，或回退调整布局

③ 协同校验（检测脚本）
   布局层 + 走线层双向检查（预防 + 检测）
```

## 思考顺序（模型动手前的六步 + 反推三问，2026-11-09）

> 来源：本日人机对照复盘。人类做法是**分区决策一次成片**（多引脚/多线在脑中同步成画），
> 顺序系统做不到"同步"，但可以**把决策单元从"单根线"提到"角色/区域"**，等价拿到并行结果。
> 每一步都有"产出物"和"判断出口"——不是灵感，是可检查的流水线。

**六步（每步产出 → 下一步的输入）：**

| 步 | 做什么 | 产出物 |
|---|---|---|
| 0 读网表社会结构 | 枢纽（扇出最大）？分层（信号 BFS）？电源族？可互换组？ | 角色清单 |
| 1 每类连接问"最短形态" | 直连/一拐/两拐各要求端点什么关系 | 放置需求清单 |
| 2 分区与通道 | 每族→哪个区、每区→哪条带（见下方分区纪律） | 走廊需求（间隙=通道的实体） |
| 3 放置 = 解需求方程 | 枢纽优先（跨坐两类邻居）；其余按层跟随；x 锚**真实目标**（列/引脚）而非行中心 | 元件坐标 |
| 4 生成后先测地板 | 交叉三分法：①拓扑不可免多→动布局/网表自由度；③走线错误多→动通道规则；②布局可减→换序 | 杠杆选择 |
| 5 改动分级 + 回退 | 局部微调数字变差两次 → 升级换模板（Rule 8）；上限三轮 | 决策记录 |

**反推三问（从走线失败模式反推布局需求）：**
1. 这根线的**最短形态**是什么？那个形态要求两端各在哪里？→ 把走线问题翻译成放置需求；
2. 这个需求对其他扇**合法吗**？谁都不合法 → 不是位置错，是**模板错**（需求互相矛盾，如 T2）；
3. **地板在哪里**？先跑三分法测下界，①占比高时禁止继续抠走线。

关键性质：**分区做对时，逐线层几乎无决策**（手绘的 1-2 拐线是分区正确后"掉出来"的）；
分区错时逐线层怎么努力都补不上。

## 分区纪律（缺省规则，2026-11-09 用户提供，黄金准则）

> 用户手绘时的实际心智模型，逐字记录后整理。缺省适用；intent 可用 `routing.zones` 覆盖。

- **Z1 区域总则**：面包板分两类电气区——**轨区**（正负轨，电源干道）与**中区**（中间孔列，元件组织区）。
  两区职责不混。
- **Z2 轨区纪律**：正负轨只承担两类连接——**板↔面包板的电源馈电**、**列↔轨/轨↔轨的跳线**。
  信号不走轨。（小电路例外：元件少时，元件的电源脚可直接上轨省掉中间区。）
- **Z3 中区纪律**：同类元件的同类引脚**合并到同一列**（一列一网，见列总线/单列即网）；
  单输入/输出对多元件 → 上面包板分发（fanout 判据，Rule 1）。
- **Z4 意图先于线**：先产出**分区表**（每族落哪个区/列、轨的用途、板脚带位置），再放置、再走线。
  分区表是模型"看到的整体画面"的文本形式（intent `routing.zones` 声明，见 intent-format.md）。
- **Z5 中继按网声明**（2026-11-09 用户提供）：**一脚多用**（源引脚唯一、消费者多个，如
  `uno:3.3V` 挂 3 个 rfid）→ 该网上面包板，**列即该脚的虚拟引脚**。电源网如此，
  信号总线同构适用（I2C SDA/SCL、共享 CS/IRQ）；**不经中继的网不上板**（mux I10-I15 直连）。
  按**网**判、不按引脚名猜（S0/S1/S2 名字像信号、电气上是 GND）。底座模式（元件插入 bb、
  引脚即孔、双重角色=中继+安装）由 `parts[].mount:"bb"` 声明（保留字，引擎未实现）。

## 可读性纪律（末端清晰度，2026-11-09 用户手理线样本提炼）

> 用户原话："交叉不可怕，端点不能糊"——**端点可区分性优先于交叉数**。交叉只要垂直清晰就可读；
> 端点被他线擦过会让两根线"看起来像接了"，这是语义级错误。我们此前的验收轴没有这一项。
> 判据脚本：`zcode-analysis/_endpoints.js`（A 项：他线内部从孔端点 <4px 擦过）。

- **C1 末端可读性**：任一孔端点 4px 内不得有他线内部穿过；末段不得与其他孔端点同排覆盖。
  验收轴：端点遮挡数只降不升。
- **C2 孔序-末端形态成列耦合**（列级批量决策）：一列接收两侧来线时，近侧线水平入口（本行），
  **远侧线垂直下落入口**（长横段抬到孔行上方，再在列 x 附近竖直进入）——同列相邻孔不得同侧同形。
- **C3 长横段跨行**：长横段不得落在任何孔行上（抬到两孔行之间或更高），否则与孔行视觉融合。
- **C4 组间留白**：器件间距要保证每根线的下降段有独立间隙；列组之间留空。
- **C10 同列可分**（2026-11-09 用户标定）：同一列的多个消费者线，落孔竖段间距 **≥12px**（按来线侧扇出：
  左侧落 col-6-12k、右侧落 col+6+12k），末段**竖直入孔**（横段走行间，Z 形：竖落→行间横进→竖直下落）。
  禁止多根线的竖落段挤在 <4px 内——图上会合并成一条粗线，分不清谁进哪个孔。代价：每根同列线多一个
  "台阶"（+2 转角）；备选：斜线收尾（1 段，3-6°）。

**反面教材**（我们的旧形态）：bus 入口 = "先降到孔行 y 再横进孔"——转弯数/车道对齐优选，
但长横段正好压在孔行上，与同列/邻列端点相撞（U3 实测端点遮挡 23 处 vs 用户手改 9 处，
而交叉数我们 13 < 用户 24）。**数字更优 ≠ 观感更好——代理指标不要当目标**。

## Rule 1: Choose wiring style

**主判据 = 电源拓扑 fanout**（与 `layout-generator.js` 一致）：

> 任一电源家族（GND / 5V / 3.3V / VIN）的板脚**需求 > 可用脚数**（Uno：GND×2、5V×1、3.3V×1、VIN×1，`boards.json powerPinCounts`）→ 声明面包板，电源走轨分发（生成器自动检测并输出 `[INFO] 电源 fanout:…`）。
> 需求 = 引用该家族板脚的连接数 + 面包板主线 1 条。例：5 个模块 VCC 全接 `uno:5V` → 需求 6 > 脚 1 → 走轨。

**面包板定位**：主用法是**离散元件插接**（电阻/LED/按钮 $bb 插孔、跨槽、同列配对），轨分发是次要收益——只走轨不插件 = 空面包板（生成器 WARN：轨连接 < 2）。离散元件直连须在 intent 写 `reason`（一句话理由），缺失即 WARN。

元件数量**不是判据**（弱参考：≤4 且电源各自独立，通常直连即可）。

## Rule 2: Functional grouping + position (layout planning)

**① Functional grouping (功能组合靠近) — plan from the start:**

- Related parts are placed TOGETHER from the beginning:
  - LED + resistor (series circuit as a group)
  - Button group (input area)
  - Sensor + display (signal chain)
- Or use breadboard to organize (complex / shared-power scenarios → parts around breadboard)
- Don't scatter related parts far apart

**② Around the board's REAL rendered area:**

- Parts must NOT enter the board's actual rendered rectangle
  (Uno 72.58×53.34, Mega/ESP32 per their viewBox)
- Not "around the geometric center" — clear the real image boundary
- Keep distance from board: enough for wire routing (≈100-500 units)

**③ Spacing for wire channels:**

- Minimum part spacing: ≥ 30 units (prevent overlap)
- Leave "wire channels" between parts (parallel lines need space)
- Pre-judge: would a wire from A to B cross another part? Adjust position early
- Large parts (LED ring / LCD / any module ≥ 60×60): keep ≥ 150 units clearance from other parts and from power-return corridors; a long rail/power line must never cross a large part's body — if it happens, move that group's `region` and regenerate

## Rule 3: Clean waypoint pattern + routing discipline

- Source pin exits on its own side first (digital up / power-analog down — see `waypoints.md`)
- Then 1-2 intermediate nodes: vertical to safe height → horizontal → vertical to target
- Same-function wires stay PARALLEL (consistent, tidy)
- Keep waypoints simple — complex multi-segment paths look messy

**Avoid converging wires (共线):** when multiple wires target the SAME pin, give each a different path so they arrive separately — otherwise the auto-router merges them into one shared line (confusing).

```json
["led1:C", "uno:GND.1", "black", ["v-120", "h10"]],     // approach from left
["btn1:2.r", "uno:GND.1", "black", ["v-120", "h-20"]]    // approach from right
```

## Rule 4: Power connections

- Direct style: part VCC/GND → board 5V/GND directly
- Breadboard style: part VCC/GND → breadboard rails → board 5V/GND
- Red wire for VCC/5V, black for GND (consistent convention)

## Rule 5: Avoid overlaps (wires AND parts)

- Don't place parts overlapping the board (blocks pins)
- Don't route wires across the board surface (blocks pin labels)
- **Wires must not overlap**: parallel lines keep ≥ 5 units spacing (not just cross-check)
- Same-target wires separated by different paths
- Don't scatter related parts far apart (unclear function grouping)

## Rule 6: 确定性走线惯例（脚本已实现，模型知悉即可）

这些是从「几何 + 网表」唯一推得的最优做法，`layout-generator.js` 已硬编码；模型不必重复判断，只用在特殊场景改意图（intent）覆盖：

- **板线分车道**：同一边（上/下）的每条板线错开一条水平车道（8px），避免共线重叠
- **错开按最终目标**：多线错开按「重映射后的最终目标孔」统计，**不按逻辑网表目标**（否则轨线会被无谓绕路）
- **LED 重叠检测足迹**：LED 视觉本体只有 ~16px 圆泡，重叠检测用 20×20，而非 40×50 容器
- **元件级偏好**（LED↔电阻同列、按钮对侧接线等）见 `layout-cards.md`，按项目实际用到的元件查阅

## Rule 7: 枢纽模块与它的去向同排（两排式 / T3，2026-11-08）

**识别（可判定）**：某模块同时连到**板脚**和**面包板/其它模块**，且它的连接数是同层最高 → 它是「枢纽」。
典型：mux（一侧 A4/A5 进板，一侧进面包板列孔，另一侧接 3 个 RFID）。

**决定**：枢纽**不堆进模块带**，而放到「板行」——与 UNO、面包板**同一 y 带**并排：
`UNO | 枢纽 | 面包板`；其余模块行叠在它们上方。行间/列间要留出走廊（板↔枢纽 ≥60，枢纽↔bb ≥60）。

**理由（实测，同一裁判）**：手绘 ref2 就是这个结构——枢纽距板右缘 59px、与板同高，
总线长 425px/线、交叉 26；生成版堆叠式是 609px/线（**+43%**）、交叉 53。

**反例（已实测，别重走）**：只把枢纽**水平**挪到板右缘、**不降到板行** → U2 硬冲突 0→6、交叉 53→66。
收益来自"同一行"，不是水平平移。

**状态**：`layout-v2.js` 已实现 T3 的**骨架/放置**（`V2_T3=1` 开启），但走线层仍是"走廊在下方"的模型
→ 开出来 U2 硬冲突 15，**默认关闭**。启用前必须先改走线：馈电/绕板/落孔柱都要按"板在侧边"重算。

**验收线**：与当前基线同口径——硬冲突 0、交叉 ≤40、转弯不升、总线长 ≤11000px。

## Rule 8: 局部改不动就回顶层（回退层级的用法）

这是「约束分级」表里 `回退层级` 一栏的执行细则。**每次改动后先看数字，再决定层级**：

| 现象 | 层级 | 动作 |
|---|---|---|
| 硬冲突 >0 或交叉上升，且改动只是**位置/常量微调** | ①→② **升级** | 不要继续调那个旋钮；回放置/骨架层，换行/换区/换模板（如 T2→T3） |
| 交叉下降但线长暴涨 / 转弯变多 | 仍是 ② | 结构没选对，继续在骨架层试下一个模板 |
| 只有 1-2 处软伤（交叉/间距），硬冲突 0、转弯不升 | ① | 允许局部微调（车道、柱位），**最多 3 轮** |

判据细节：**"单纯移动元件、走线方案不变"只允许用在 ①；一旦数字变差就说明该方案的空间假设错了，
必须回到 ② 重新布局+重新连线**（`layout-v2.js` 每次生成都会全量重路由，所以"重新连线"是免费的）。
本轮教训：把枢纽行水平平移（①）失败后继续在那条路上调，等于违反这张表。

## Wiring colors (convention)

Common wire colors: `green`, `red`, `black`, `yellow`, `blue`, `orange`, `purple`, `white`.
Convention: red = VCC/5V, black = GND, others = signals (distinguish by color).
Empty color `""` = hidden wire (e.g. `$bb` breadboard auto-routing).


## Rule 9: 输出档位（prototype / matrix / device，2026-11-13）

**指标最优 ≠ 现实最优。** 完全隔离 + 跳线矩阵能到「交叉 10 / 硬冲突 0」（用户手画 `_evalt2`），
但连接数 +60%、面积 +10%，且不考虑装配与维护——所以它是**可选档位**，不是默认。

- 未声明 = `prototype`（共用轨/列，少线，视觉清晰，适合面包板原型与教学）；
- `routing.profile = "matrix"` + `reason` 才启用矩阵档（母线中继列 + 一网一列 + 列↔列跳线）；
- `device`（产品内部：线束/固定/维修可达）**引擎不支持，必须显式声明不支持**，
  不得让模型误以为 matrix 等于产品级；
- 任何母线/中继/隔离列 → **强制生成 `wiring-notes.md` 跳线台账**：
  逐网写明「母线列位置 / 分发跳线 / 这一组的作用」，让人能看懂也能按条手改；
- 完整规格见 `wiring-profiles.md`（含触发/禁止条件、`relays[].role` 扩展 `bus`/`isolation`、matrix 验收线）。


## Rule 10: 跳线台账（wiring-notes.md）——每个网的作用必须可读

**产出**：`node scripts/wiring-notes.js <projectDir>`（生成器已自动调用；`V2_NO_NOTES=1` 可关）。

**做法**：不做"按连线猜网名"，而是**电气网络重建**——
列/轨/引脚作节点、线作边，并查集求连通分量，**每个分量 = 一个电气网**。
于是 bb↔bb 的裸跳线也能正确归网（它们不带网名）。

**每节输出**：

| 内容 | 说明 |
|---|---|
| 网名 + 根数/端点数 | 由网内已知引脚名归一（`5V` 与 `VCC` 同类；`3.3V`、`GND`、`SDA`、`SCL` 各自成类） |
| **形态作用** | 四选一：电源干道 / 母线中继 / 列隔离 / 直接连线 |
| 形态清单 | 板脚→轨、板脚→列、轨→列、列↔列、元件→列，逐根列出 |
| ⚠ 疑似短路 | 跨电位类被连通（如 GND 与 5V 落在同一分量）→ 直接报错 |

**实例（用户手画 U3b，`_evalt2`）**：

```
## 网：SDA（8 根）
形态作用：母线中继：入口 → 母线列 → 列↔列分发到各元件列
- 板脚→列：uno:A4 → bb1:4t.a
- 列↔列：4t.b→17t.a（母线中继列 17）→ 17t.d→27t.d(mpu)、17t.e→22t.d(rtc)、17t.c→15b.f(oled)
- 元件→列：mpu1:SDA→27t.e、rtc1:SDA→22t.e、oled1:SDA→15b.j
```

这段就是用户说的"绿色 SDA 先在下半区做中继再分发"——台账让它**自解释**。

**为什么这属于 skill 而不是模型自由发挥**：
1. 归网、形态分类、短路检查都是**确定性计算**（脚本）；
2. 模型只负责在 intent 里**声明意图**（`routing.profile`、`routing.relays[].role`）；
3. 台账是**验收物**：模型与人（用户）都能对着它检查"这组线打算干什么、实际干成了什么"。

## 约束分级（硬约束 / 软约束 / 灰度开口）

> 核心原则：把「穿元件」和「交叉」分开——穿元件是硬伤（现实里接不上，必须绕），交叉是软伤（现实里跳线交叉是常态，可妥协）。脚本兜底给安全默认，模型在 intent 里可覆盖。

### 硬约束（必须满足，违反 = 不合格）

| 冲突 | 说明 | 处置 |
|------|------|------|
| 线穿元件（hits-part） | 线从元件本体中间穿过 | 必须绕开 |
| 元件重叠（parts-overlap） | 两个元件本体重叠 | 必须错开 |
| 元件在板子上（part-on-board） | 元件压在板子本体上 | 必须移开 |
| $bb 对不齐（bb-misaligned） | 引脚偏移 > 0.5px，网页版不渲染插接绿点 | 必须精确 |
| 线穿板（wire-through-board） | 线横穿板子本体 | 必须绕开 |
| 引脚不存在 | pin 不在 pins.json / 板型配置 | 跳过该线并告警 |

### 软约束（尽量优化，可妥协）

| 冲突 | 说明 | 处置 |
|------|------|------|
| 线交叉（cross） | 两条线相交 | 尽量少；I2C 反序这类不可避软伤可妥协 |
| 共线重叠（overlap） | 多线合并成一条 | 尽量错开 |
| 线长 | 绕远 | 尽量短，非硬指标 |

> **I2C 反序豁免**：Uno 的 A4=SDA 在 A5=SCL 左边，而 OLED 模块 SCL 在 SDA 左边，两条线必然交叉一次。妥协「交叉」、坚持「先离开元件再走线」。

### 灰度开口（C 类，模型决策，脚本给默认）

| 字段 | 含义 | 默认值 | 备注 |
|------|------|--------|------|
| 交叉容忍度 | 允许的交叉上限 | 反序豁免 + 其余尽量少 | 模型可设「每线最多 N」或「全局 ≤ N」 |
| 扩容方向 | 区域放不下时往哪扩 | 朝远离板子方向（right 往右、bottom 往下） | 脚本默认，模型可覆盖 |
| 扩容上限 | 扩容边界 | 不越出画布 / 不侵占相邻区 | 超限自动触发回退改组 |
| 回退层级 | 解决不下的升级路径 | ① 局部扩容（脚本兜底，便宜）→ ② 回顶层改组/换区（交模型，贵） | — |
| 迭代轮数上限 | 回退重排最多跑几轮 | 3 | 模型可设 |

### 与 A/B/C 的关系

- **A 类常量**（几何数据、板型配置）→ 提取器固化，不变
- **B 类可推导**（走线算法）→ 从硬规则改成软约束优化
- **C 类灰度**（容忍度、扩容方向、回退层级）→ 模型决策，脚本兜底

## 交叉三分法（2026-11-07 定稿判据，工具 `wokwi-bench/classify-crossings.js`）

「交叉多」不是一个可执行的结论。把每个交叉配对按**可计算判据**分成三类，分别归不同工序处理：

| 类别 | 判据 | 归属 | 处置 |
|---|---|---|---|
| ① 拓扑不可免 | 两端顺序颠倒（`(srcA.x<srcB.x) !== (tgtA.x<tgtB.x)`）**且**源端或目标端是**同一元件**（引脚在同一本体上焊死，换序不可能） | 判据豁免 | 不计入优化目标；它是该电路交叉数的「地板」 |
| ② 布局可减 | 顺序颠倒，但两端分属**不同元件**（换左右顺序 / 镜像元件即可消除） | 布局层 | 按目标引脚 x 排序、大件外置、必要时镜像 |
| ③ 走线错误 | 顺序**没颠倒**却仍相交（绕路、回头、重叠造成），或伴随共线重叠/穿件/同孔复用 | 走线层（bug） | 必须修：走廊分配、离体阶梯、轨外侧入孔 |

**工作流（按杠杆排序）**：

1. 先跑分类器：`node wokwi-bench/classify-crossings.js <项目目录>`
2. **③ 优先修**——它是 bug，量最大且修完不牺牲可读性（U1 实测 45/76 = 59% 属此类）
3. **② 次之**——布局排序/镜像，收益稳定（U1 18、U2 20）
4. **① 豁免**——不要为了让数字好看去拆合法的交叉；手绘图的交叉里同样含这三类，所以「交叉 ≤ 手绘×1.2」这种比法要改成「③=0、②尽量小、①豁免」

**为什么这样分类对模型有用**：它把「该改算法的」和「该改布局的」分开，避免模型在布局层反复试错去修一个本来就是走线 bug 的交叉；同时给了判据一条明确的终止条件（③=0 即布线层完工）。

## 走线方向即语义（2026-11-07，从用户手绘 ref1/ref2 实测归纳）

> 一条线的 `from`/`to` 不只是电气配对，它决定了**从哪里离体、从哪里进脚**。写反了，
> 几何上就是「从板体内部起步/穿板而入」——用户肉眼可见，但很多检查器看不见。

### 方向约定（实测统计）

| 手绘图中的方向 | 条数（ref1/ref2） | 语义 |
|---|---|---|
| 元件 → 板脚 | 7 / 2 | 信号：从元件侧离体，到板脚开放侧进入 |
| 元件 → 面包板孔/轨 | 12 / 12 | 取电或中继：从元件离体，就近落孔 |
| 板脚 → 面包板轨 | 2 / 2 | **馈电**：板子向下离体，落到轨上（板是起点） |
| 板脚 → 面包板孔 | 0 / 1 | **中继的板侧半段**：板脚起、落孔，中间靠板内连通 |
| 轨/孔 → 轨/孔 | 3 / 4 | 桥接/跳线 |

### 两条原理（写进规划层，供模型与生成器共同遵守）

- **P-方向**：起点 = 其引脚开放侧**朝向对方**的那一端；终点 = 目标端（从目标引脚的开放侧进入）。
  - 底边脚开放侧向下、顶边脚向上、左边脚向左、右边脚向右；
  - 板子底边脚（A0-A5/电源）**首段必须向下离开板体**，再横向——绝不上穿板体；
  - 元件在板下方时反过来：板脚向下即朝向元件，此时**板当起点**。
- **P-中继**：用面包板做中继时，两段各自按自己的开放侧起步（元件→孔、板脚→孔），
  中间靠「同列同半区」内部连通——这是手绘图把长线切短的核心手法（见 breadboard.md P3）。

### 可判定化（待接进裁判）

对每条线解析首/末段方向，与两端引脚的开放侧比对：
- 首段不与源引脚开放侧一致 → `escape-wrong-side`（提示级）
- 末段不从目标引脚开放侧进入 → `approach-wrong-side`（提示级）
- 末段穿越目标元件/板本体 >15px → 已是硬冲突（wireThroughPart / wireThroughBoard）

## 引脚次序的通用规则与模型分工（2026-11-07）

> 用户问题：SDA/SCK 的线序规则是否也适用于其它元件？旋转后的次序怎么办？这种判断要不要交给模型？

### 分工边界：脚本管"次序怎么排"，模型管"元件怎么摆"

| 内容 | 归属 | 说明 |
|---|---|---|
| 给定元件+旋转+出线边 → 引脚沿边次序 | **脚本**（确定性） | pins.json 引脚坐标经旋转重投影后排序，任何元件通用，不允许元件特判 |
| 同边多线的车道/孔位分配（束不拧） | **脚本** | 次序即规则：沿出线边第 k 个引脚 → 第 k 档车道/孔位 |
| 元件该不该转、哪条边朝走廊 | **模型**（intent 声明） | 构图可读性判断；不声明则脚本按"最近边"几何默认 |
| 多边引脚元件的分组走边（如 MUX 信号走左、电源走右） | **默认脚本、模型可覆盖** | intent 可写 `orientation.pinEdge` / `bundleHints` |

### 旋转后的次序（关键：完全可算）

元件旋转 90°/270° 后，原纵向引脚列变横向，出线边随之改变。脚本流程：
**先按旋转（含 _rot90 校准）算引脚绝对坐标 → 再投影到出线边 → 再排序**。
模型永远不需要心算旋转后的次序，只声明"这个元件转 90°、引脚列朝板"。

### intent 声明样例（模型侧只写一句话级声明，不写坐标）

```jsonc
{ "id": "mux1", "type": "board-cd74hc4067",
  "orientation": { "pinEdge": "right" },
  "bundleHints": { "SPI": "left", "power": "right" } }
```


## 规则分级与冲突裁决（2026-11-10 审计：这一轮的新规范与既有规范的对照）

> 背景：为复现用户手画的 U2 布局，本轮逐步加了一批"规范"（单消费者直连 / 一族一轨 /
> 3.3V 免双轨桥 / 簇分列 / 同带直连 / hub 布局）。本节回答：**它们与既有规范冲突吗？是不是又 Case-by-case 了？**

### 1. 对照结论（逐条）

| 本轮新规范 | 既有规范 | 关系 | 裁决 |
|---|---|---|---|
| **hub 布局**（mux 进 bb 带、板下移留槽） | **Rule 7 枢纽同排（T3，2026-11-08）** + 引擎已有 `V2_T3` | **重复实现** ✗ | ①：把电源规则并入 T3，删掉 ad-hoc 的 `V2_HUB_PART` 分支（两套机制同一规则 = 架构债） |
| **单消费者直连**（mux 5V → 板脚） | Rule 4 "Direct style" + 既有坑：*"S0-S2 直连 GND.2 会绕出 457px 下探怪线"* | **与坑冲突** | ②：直连需条件——两引脚**离体方向一致**且**跨度 ≤ 阈值（≈250px）**；否则走轨。写入 Rule 4 的判定式 |
| **一族一根轨馈电 + 轨→列跳线** | Z2（轨只做馈电/跳线）、Z3（同类引脚并一列） | **细化** ✓ | 保留，写成 Z2 的补充："一网一根轨馈电；列由轨跳线供电" |
| **GND 分簇成两列**（mux 组 / rfid 组） | **Z3：同类元件的同类引脚合并到同一列** | **表面冲突** | ③：Z3 加限定——"**同一簇内合并**；跨簇按最近列分列（≥2 列间距）"。多簇是"就近 + 少交叉"的必然，不是例外 |
| **3.3V 借 tp（免 tp→bp 桥）** | 静态轨分配（GND→tn, 5V→tp, 3.3V→bp） | **资源冲突** | ④：轨是**可租借资源**：优先 GND tn / 5V tp / 3.3V bp；**若先序族直连或未用则该轨让位**（并记录租借关系，禁止跨网共用） |
| **同带直连短形态** | **C8：长横段抬到 bb 上方** | **边界冲突** | ⑤：按**跨度**分——跨度 ≤ 2 孔距（19.2px）用同带短直连；> 阈值抬面外。写成 C8 的量化条件 |
| **簇列就近** | **包裹序 / 块位 / 等距列位**（单行布局） | **作用域不同** | ⑥：**按模板绑定**——单行(T2) 用包裹序+等距；枢纽同排(T3) 用簇就近+分簇。不是二选一，是"模板声明规则集" |

### 2. 结构性结论：把"按模板绑定"写进框架

**规则不冲突的前提是"模板 → 规则集"显式声明**，否则每次换布局都在改规则：

| 模板 | 布局特征 | 绑定的规则集 |
|---|---|---|
| **T2 单行** | 模块一排 + 板在下/侧 | 包裹序、等距列位、均匀分布、行距 170、四道馈电嵌套 |
| **T3 枢纽同排** | 板 \| 枢纽 \| bb 同一带 | 簇就近分列、一网一轨、单消费者直连（带条件）、枢纽留槽 60、簇内合并 |
| （未来）多 bb / 插入式 | `mount:"bb"` | 待定 |

### 3. 优先级（冲突时的裁决顺序）

```
1 硬约束（穿板/穿件/共线/方向/孔一一对应）
2 不变量（平行间距 ≥9.6、端点不被异网压住、最小转弯）
3 布局类（带结构、行距前提、外框矩形度）
4 结构选择（电源拓扑：直连/轨/列；分组；簇）
5 局部形态（同带短直连 vs 面外横段、收尾 stub vs 微斜）
```

低层规则只有在高层规则**不可满足或代价过大**时才让位，且必须写明让位条件（不是隐性妥协）。

### 4. 现在就要做的三件事（在继续生成之前）

1. **合并重复实现**：`V2_HUB_PART` 的布局逻辑并入 `T3` 模板（保住 hub14 的电源规则），
   只留一个枢纽同排入口；否则以后每次改都会两边不一致。
2. **把 ①③④⑤ 的"条件"写进对应条目的正文**（Rule 4 / Z2 / Z3 / C8），
   并在生成器里落成显式判定（而不是散落的 `process.env` 分支）。
3. **给 T3 建回归样本**：像 T2 那样钉住 `[WARN] 前提`（行距、槽宽、轨租借），
   边缘回归集扩成 `{T2, T3} × 行距 × 直连/轨` 组合。

## 7. 手改友好度（hand-fixability）：从"压低交叉"转向"可被用户几笔改好"

> 用户 2026-11-12 定调：视觉已清晰时继续压交叉收益很低；真正的目标是
> **用户只需手拖几根线就能更清晰**。因此规则优先级改为：

### 7.1 一级不变量（用户列举的"更重要"项）

| 不变量 | 判据 | 现有工具 |
|---|---|---|
| **不共用端点** | 同一孔/脚不得被两根线同时占用（除电源网内合法并束） | `score-diagram.js` 的孔占用检查；`_endpoints4.js` |
| **端点不被遮挡** | 孔的进线方向上的邻孔/邻线不压住端点（异网才算） | `_endpoints4.js`（吸附模型） |
| **端点不乱序** | 沿出线边的第 k 根线 → 第 k 档车道/孔位，束不交叉 | `assignLetters`（C2 孔序）；`_spacing.js` |
| **不共线重叠** | 平行段 ≥ 一个孔距 9.6 | `_spacing.js` |

这四条都是**"手改友好"的前提**：乱的端点、被压住的孔、乱序的束，用户拖一根线就全乱。

### 7.2 二级（可读性，允许妥协）

- 交叉数（只有"局部可见、拖一根线就能消掉"的那类值得追）
- 嵌套层数（越少越好：外层包裹内层，但不超过 2–3 层）
- 转弯数（≤3/线 ≈ 现状 2.7–3.0）

### 7.3 三级（不动手的底线）

- 硬冲突必须 0（穿板/穿件/共线/孔一一对应）
- 外框不越界

### 7.4 实验记录：全隔离（每元件独立一组电源跳线）不可行

`V2_ISOLATED=1` 实测（U3b）：**hard 19**（穿件 8 / 穿板 4 / 共线 6）、交叉 48、间距违规 27。
原因：面包板只有 **5 个块 × 5 列 = 25 可用列**（含分隔），而 U3b 的"每元件每网一组"需要
GND×3 + 5V×3 + 信号中继 ≈ 7–8 组 → **列位容量不足**，只能强行共用列 → 孔冲突与共线爆掉。
→ 结论：**隔离度受列位容量约束**，不是"不怕重复接线"就能解决；共用列/轨才是经济解。
（该实验保留 `V2_ISOLATED` 开关与列位耗尽兜底，后者修掉了一个真实崩溃。）
