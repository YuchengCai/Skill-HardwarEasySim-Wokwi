# 需求入口与选型交接（序列3/文档44）

共享入口先判断用户给了什么，再决定下一步。模型负责理解需求与选型，脚本负责几何与检查。只读本文件，不需要先读历史文档 26/28。

## 入口分诊

| 用户给了什么 | 下一步 |
|---|---|
| 功能目标，委托选型 | 复述必要的功能关系；沿用已有器件，推荐器件类别/型号并给简短理由。只要采购建议就停在选型；同时委托制作时，先让用户确认会改变功能或接法的选择。 |
| 元件清单 / 引脚表 / 已有接线 | 沿用已确认事实；连接充分时直接绘图。把必须保留的物理端点与可自由分配的位置分别写入意图（显式孔位=锁定，其余自动）。 |
| 粘贴代码 / 提供工程 | 追踪生效的板卡配置、初始化与调用；信息足够本次交付时直接绘图。库名/地址/变量名可作线索；证据冲突时指出具体接点。只委托绘图时保留源程序。 |
| 只有商品名 / 所购规格 / 照片 | 判断哪些信息会改变实际接法。能收图且能读图时用近照；纯文本可请用户抄录丝印。**只问能区分剩余接法的一项**，保留其余已知连接。 |

## 交给绘图步骤的最小内容

- 本次交付目标（静态图 / 采购建议 / 代码 / 烧录）
- 已选实物或器件类别（能确定的型号）
- 已证实的信号与去向（网络、板脚、模块引脚）
- 锁定孔/锁定端点与允许变动项
- 替代图例与实际丝印对应关系（仅涉及实物替代/插座时读 `references/common/static-wiring.md`）
- 会影响实接的待核实项（明确标 unknown，不填默认值）

## 确认节奏

- 用户确认前：可整理已知接点或可复用规划；用户也委托代码时，先准备与待选器件无关的代码结构。
- 改变功能或接法的选择必须先确认；普通对话在下一条回复续接。
- 用户改选时应用最新意见，再更新受影响的元件、连接与交付说明。
- 只做原理示意时可带明示假设继续；实接依据不足时将对应接点保留待核实。

## 验收（文档44）

1. 同一需求「已有 Uno，希望看室温」分别委托采购与出图：保留 Uno；解释传感与输出选择；采购任务结束；制图分支确认前把显示屏改为串口输出，撤掉显示屏及其接线、保留测温关系。
2. 分别投入：连接已确定的工程、只知 A0 的程序、程序与笔记冲突的工程 —— 观察是否直接出图/只追问器件/只追问冲突点；换一个未示范的接口复跑。
3. 给出带两个版本的商品名，随后补一处丝印：纯文本与视觉入口都能接续；核实深度与交付匹配。

完整原型拆解、新建完整代码生成与功能仿真另期。
