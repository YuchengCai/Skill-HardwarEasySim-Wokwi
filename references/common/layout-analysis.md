# 布局分析方法（与具体布局无关）

> 目的：换一种布局（单行/双行/板在侧/多板/更多元件）时，**不靠加规则**，而是用同一套分析法
> 推出该布局应有的车道序、走廊宽度与交叉下界。工具：`zcode-analysis/_intervals.js`。

## 0. 一句话

把图抽象成**带 + 区间**，车道序取**区间嵌套序**，走廊宽度 = 层数 × 孔距；
带宽不够就改布局，改不了就是结构性交叉（下界）。

## 1. 四步分析法

### 第 1 步：划带（band）
把所有 part 按 y 排，落成若干水平带（同排元件同一带；面包板/控制板各自一带）。
带之间是**走廊**（放横段的地方）。

### 第 2 步：算区间
每个网的端点落在哪些带 → 得到区间 `[最上带, 最下带]`。
例（U3b-alignA）：

| 网 | 区间 | 跨带数 |
|---|---|---|
| GND | [0,4] | 4 |
| 5V | [0,4] | 4 |
| SDA/SCL/VCC | [0,3] | 3 |
| 板脚→bb（other） | [3,4] | 1 |

### 第 3 步：定车道序（外缘包内缘）
**跨带数越大 → 车道越靠外**（跨 4 带的 GND/5V 最外，跨 1 带的板脚桥最内）。
这条不是风格偏好，是几何必然：外层区间包含内层区间时，按此序排不会新增交叉；
反序则必然交叉。→ 这就是"外缘包裹内缘"的可证明版本。

### 第 4 步：算走廊需求 + 交叉下界
- **车道层数** = 该走廊上通过的网数；**最小宽度** = 层数 × 9.6px（一个孔距）。
- **带间结构性交叉** = 互不包含但有重叠的区间对数（工具输出）。
  例：U3b-alignA 与 U2r 都是 **0** → 说明带级布局没有制造交叉。
- **带内结构性交叉** = 同排元件的引脚顺序决定（用 `classify-crossings.js` 的 ① 类统计）。
  例：U3 的 ① 约 22-28 —— 这才是我们交叉的主要来源，属于引脚顺序（不可免）。

## 2. 判定表：布局是否够用

| 检查 | 判据 | 不够时怎么办 |
|---|---|---|
| 走廊宽度 | 层数×9.6 ≤ 行距 − 净空 | 加大行距 / 减少该走廊的网（改分组） / 分侧绕行 |
| 带间交叉 | 区间交叉 = 0 | 调换带的顺序（元件换行） |
| 带内交叉 | ① 类 > 0 | 换元件左右序（②类）或接受（①类不可免） |
| 端点/间距/方向 | 硬冲突 0、间距 ≥9.6 | 避让 + 兜底（见 layout-rules） |

**实测对照**：U3b 行距 170、车道 6 层 → 需求 58px，余量充足；
行距压到 150 时走廊被挤压 → 模块线穿板（这就是"行距 ≥170"这条前置条件的来源）。

## 3. 多行布局（U2）的分析结果

U2r：GND/3.3V 跨 5 带（最外）→ SDA/SCL 跨 3 带 → mux 控制 跨 2 带 → VCC 1 → 5V 0。
共 7 层 → 需求 67px。**当前 U2r 没有按这个序排车道**（仍用旧的 staging），
所以交叉 44（U3 为 38）——这正是下一步该做的地方，而不是继续给 U3 调参。

## 4. 新布局的作业流程

1. `node zcode-analysis/_intervals.js <新布局>` → 带、区间、车道序、宽度需求、带间交叉；
2. 按判定表调布局（行距/带的顺序/分组）；
3. `classify-crossings` 看带内 ①/②/③；
4. 应用不变量（间距 9.6、端点、方向）+ 前置条件 + 兜底；
5. `_edge-sweep.js` 跑组合回归（任何组合不得出现不可接受硬冲突）。

## 5. 缝宽（间隙）由过线数算出，不是拍数值（2026-11-10）

**规则**：相邻元件/板/bb 之间的缝，需要的宽度 = 该缝通过的线数 × 9.6px（一个孔距）+ 12px 余量。
即 `need = N × 9.6 + 12`；`N` = 穿过该缝的竖线根数（工具实测）。

**工具**：`node zcode-analysis/_clearance.js <diagramDir>` —— 输出每条缝的「缝宽 / 过线数 / 需要 / 是否不足」。

**实测（U2 hub 布局）**：

| 版本 | mux↔bb 缝宽 | 过线 | 需要 | 结论 |
|---|---|---|---|---|
| seam=60（旧） | 60 | 5 | 60 | ✓ 零余量 |
| 用户手改版 | 60 | 6 | 70 | ✗ 差 10px |
| seam=80（现） | 80 | 7 | 79 | ✓ |

→ 用户直觉正确：mux 与 bb 之间原本不够宽。生成器已改成按「枢纽连接数估算 → seam = max(80, N×9.6+12)」放置。

**推广**：这条同样适用于板↔bb、rfid↔rfid、模块↔模块的每一道缝；生成后用 `_clearance.js` 复查，
不足则调布局（加大缝距或减少该缝的过线数）。

## 6. 决策轨迹（V2_TRACE）与两个反例（2026-11-12）

**V2_TRACE=1**：每根线打印一行 `wire | escRule | dir | stageY | kind | hole`。
用途：当"改了参数没效果"时，一次运行就能看出**哪条规则决定了这个值**，不必盲猜代码位置。
本项目在这条杠杆上曾连错 3 次（`sideOfMod` / `escEst` / 顶层出线），trace 一次定位。

**反例 1（缝负载失衡不是缺陷）**：U3b 里 mpu↔rtc 缝过 8 根、rtc↔oled 缝 0 根。
按"朝目标出线"把 oled 改到左侧空缝 → 交叉 **38→48（更差）**。
原因：**外侧绕行虽长，但完全不碰内部束**；内侧会与 rtc/mpu 相互切割。
→ 结论：缝的负载不均可能是**正确选择的结果**，不能只凭"空缝没被用"就判定浪费。

**反例 2（RTC 左脚是物理约束，但不是交叉来源）**：RTC 引脚固定在左缘 → 只能左出线。
但实测它 4 根线并非拥挤主因；强行翻侧会带来新交叉（同上）。

**工程教训**：JS 正则 `[+-]` 是**空字符范围**（不是"加或减"），必须写 `[-+]`；
本项目的实验开关因此静默失效过一轮。
